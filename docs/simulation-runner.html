Inside the Simulation Runner

The runner flies your constellation as an operated system and writes the epfd statistics a filing is judged by. This page explains which input supplies what, why the operation profile is mandatory, and what the optional R set changes when you add it.

One run, three files

A simulation needs two different kinds of truth: where the satellites are, and what they do. The window keeps them in separate files so each can be authored, reviewed and swapped on its own — and both are required. A third file — the declared operating parameters — is optional: when present it swaps the scheduler's gates for the declared constraints.

The orbit design document

An *.orbitdesign.json saved from the Orbit Design tab. It is the space segment and nothing else: every shell's orbit geometry, planes, phasing and repeat declaration, from which the runner rebuilds the constellation and propagates each satellite. It says nothing about payload, power or scheduling — deliberately, so the same constellation can be flown under different operations.

One quiet coupling: the first shell's operating height anchors the payload's beam-layout altitude — the profile carries no altitude of its own.

The operation profile

An *.opprofile.json saved from the Operation profile window. This is the operated system in one file: the payload (beam pattern, layout, transmit power, frequency-reuse aggregation), the link discipline the real system enforces (minimum elevation, GSO exclusion, capacity caps, minimum hold), the service geography, the scheduling policy, the activity duty — and the downlink footprint source, which picks between the live scheduled beam composition and a declared PFD mask.

The profile is required — the runner refuses to fly without one, and there is deliberately no stand-in payload behind it: a run that is meant to say anything about a real system must be a run of that system, transmission basics included. The profile supplies the whole system side — the downlink frequency and the minimum elevation among it — so the remaining fields describe only the victim and the run.

Tech · the mask footprint path

With declared PFD mask as the footprint source, epfd(down) is computed the examination's way: the mask XML is read per Recommendation ITU-R S.1503-4 §D5.1.4.1, interpolating the latitude blocks as §D5.1.5 prescribes. No epfd(is) byproduct is written on this path — the in-space direction needs the e.i.r.p. masks, which a pfd mask does not carry.

The operating params (R set) — alternative gates

An *.opparams.json from the Operating parameters designer — the declared constraints, and the one optional input. When set, the scheduler obeys the declared pointing and scheduling constraints — minimum elevation per latitude, the exclusion angle, the co-frequency caps — instead of the profile's enforced gates, in both link directions. The payload, its power and everything else transmission-side still come from the profile: the truth payload flown under the declared discipline.

That comparison is the point. Run the same profile twice — once on its own gates, once under the derived R set — and the two CDFs show what the declared envelope costs or allows relative to the operation it was measured from.

Tech · how the gates are read

The per-latitude arrays are read the way S.1503-4 Part B defines for the R set: minimum elevation at the nearest latitude row, the exclusion angle by linear interpolation between rows. Quantities the set does not declare fall back to its header values, and an absent header is permissive.

The victim and the run

The loose fields below the file pickers describe the other side of the interference geometry and the sampling of the run:

  • Victim GSO longitude — the wanted satellite for epfd(down), the victim satellite for epfd(up) and epfd(is).
  • Victim ES latitude / longitude — the earth station the downlink statistics are collected at; also the in-space victim's boresight point.
  • ES dish diameter — the S.1428 pattern diameter of the victim earth station (down); it also stands in for the transmitting earth station (up) when the profile's uplink side declares no dish of its own.
  • Duration / time step — how long and how finely the operation is marched. Statistics of rare deep events need runs long enough, and steps fine enough, to catch them.

The uplink transmit power, its power-control reference elevation and its frequency are transmission basics and come from the profile's uplink side, not from this window.

▶, ⏩ and Write CDFs

The two icons animate one continuous timeline: ▶ advances one simulation step per tick with everything drawn — satellites, candidate links (thin) and granted links (thick) — and ⏩ advances many steps per tick, drawing sparsely. Pressing the other icon mid-run only changes the pace; the clock and the scheduler state carry on. Neither collects statistics.

Write CDFs… is the statistics run: no map updates, the full step count on a worker thread, and three CSV files — .down, .is and .up — each a cumulative distribution of epfd at the victim.

Tech · the CDF files

Levels are binned in the 0.1 dB bins of S.1503-4 §D7.1.2, and each file reports the step count, the quiet steps (nothing visible or transmitting) and the maximum epfd seen. The runner deliberately stops at the distribution: verdicts against a limit — the §D7.1.3 comparison — belong to the compliance loop, which reuses these same mechanics victim by victim.
