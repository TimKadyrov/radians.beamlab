Inside the R Set

The Operating parameters (R set) window writes one R set: the operating constraints a non-geostationary (non-GSO) filing declares beside its power flux-density (pfd) and e.i.r.p. masks. You type the values or fill them from a compliance-loop run, review them, then save the set as JSON or export it as XML.

Two ways to fill it

  • Type the values when you know them in advance: to copy an existing filing, or to write a deliberately conservative set.
  • Derive & fill when you do not. It fills the fields from the set the compliance loop wrote for your operation profile. It runs no simulation.

Either way you end with the same editable fields. A derived set is a starting point to review, not a verdict.

What the R set declares

The masks declare power: how strongly the satellites radiate in each direction. The R set declares the rest: where and when a satellite may serve, and how many may serve together. The examination under Rec. ITU-R S.1503-4 enforces these constraints alongside the masks.

The profile’s selection strategy, demand and traffic activity have no field here. They reach the filing only through the constraints they obey.

Filling in the fields

The left column holds the single values:

  • Identity and frequency: sat_name, ntc_id and param_id identify the set; low_freq_mhz and high_freq_mhz give the band it governs.
  • Earth-station population: es_density, es_distance, es_lat_min and es_lat_max.
  • Header constraints (empty = omitted): min_angle_at_sat, min_angle_at_es, max_co_freq, max_co_freq_sat, min_duration and elev_angle. An empty box is left out of the XML.

The four boxes on the right are the arrays. Each takes one node per line, in the format its header shows:

  • min_exclude: orb lat alpha, where orb 0 means all orbits;
  • min_elev: lat az elev. Lines with the same lat form one latitude, read across azimuth, so write a floor that does not change with azimuth at az 0 and az 360;
  • max_co_freq: lat value;
  • min_duration: lat seconds.

Numbers take a decimal point. Counts, seconds, orb, ntc_id and param_id are whole numbers. Most fields show their parameter card as a tooltip; sat_name, ntc_id, param_id, high_freq_mhz, es_distance and es_lat_max have none.

Under the buttons, a grey line counts the nodes in each array. A red line reports a typing error with its field and line number, a set filed in both forms, and the result of each button.

Header or array: one form each

Three quantities come in two forms: one header value, or a per-latitude array. The header elev_angle is the single-value form of min_elev; max_co_freq and min_duration use one name for both. File each quantity in one form only.

A set that files one quantity in both forms is an invalid filing. The red line names the quantity. Export R XML… refuses the set, and the Simulation runner and the Compliance loop refuse to use it. Save set (JSON)… still saves it, with the warning.

min_exclude exists only as an array. The other header fields exist only as single values.

A quantity you leave empty in both forms constrains nothing. It costs nothing in the examination, and it promises nothing. An array reaches every latitude: beyond its outermost row, that row applies. So one row declares one value everywhere, and the outermost rows must hold for every latitude beyond them. Declare what the operation does, where it does it.

Tech · how the set is read

S.1503-4 reads the min_elev, max_co_freq and min_duration arrays at the nearest latitude row (§D5.1.5, step 1), and min_exclude by linear interpolation between latitude rows (Part B). The app reads them the same way wherever it runs a set. Within one min_elev latitude, elevation is interpolated linearly in azimuth, the end rows applying beyond them. Every read is total: beyond the outermost row, that row applies. An orbit’s own min_exclude rows replace the orb 0 rows for that orbit. S.1503-4 does not say what a set filed in both forms means, so the app refuses such a set rather than choose a precedence. Undeclared quantities impose nothing: an elevation floor of 0°, no exclusion, no co-frequency caps, no minimum duration (the classic algorithm) and minimum angles of 0°.

Derive & fill

The Derive from the compliance loop group fills the fields from a compliance-loop run. Enter the profile’s *.opprofile.json in Operation profile, or pick it with Browse…, and press Derive & fill.

The window reads the R set of the compliance-loop run made from that profile. It fills every field from it except sat_name, ntc_id, param_id, low_freq_mhz and high_freq_mhz: the identity and the band belong to your filing and stay as you entered them.

It runs no simulation. The loop has already derived the set, and the loop’s own checks used it; a second derivation here could disagree with it. The run’s duration, time step and latitude step decide how much of the system the derivation saw, and they are set in the Compliance loop window.

If that run was given a set in Declared R set (optional) instead of deriving one, the set it wrote, and so the set read here, is the given one.

The red line names the run it read, by date and file, or says why none qualifies:

  • No profile. Pick one first.
  • No run, or the run is older than the profile file. Press Run loop in the Compliance loop window. It derives the set as its first step.
  • A run of the same name was made from a different profile. Give this profile its own name, or run the loop for it.

Load set… can also open a run’s *.operparams.json directly. It then also takes the run’s identity and band, which in a derived set are placeholders.

Tech · how the run is found

Runs are filed under the profile’s Profile name: the name up to any bracket, lower-cased, with every character other than a letter or digit turned into a hyphen and hyphens at the ends dropped. The run directory is dataset\margin\<name> in the folder that holds this page’s docs folder, and the set is <name>.operparams.json. A run counts only when that file is newer than your profile file and, when the run keeps a copy of the profile it ran, that copy matches your profile. Two profiles whose names differ only in brackets share one run name.

What the derivation writes

Run loop derives the set before it measures anything else. A saturated probe runs the system with no victim earth station, demand raised to the profile’s co-frequency cap when it declares one, and activity factor, operational fraction and illumination duty cycle at 1. The probe runs for the loop’s duration and time step. Every link it grants is measured, and the set envelopes the measurements:

Each array row stands for a latitude band as wide as the loop’s latitude step, placed at the band’s centre. A quantity the probe never observed stays empty; nothing is guessed. The header forms elev_angle and max_co_freq are not written: those quantities come as arrays. min_duration is never written: declaring it would switch the examination to the track-duration algorithm of S.1503-4 §D5.1.4.2.

Tech · the exclusion rows

min_exclude is read by interpolation between rows, so each row also governs part of its neighbouring bands. Each band’s smallest angle is therefore first lowered to the smallest of its own and its two neighbours’ values. Rows of 0.05° or less are then written as 0°, since a near-zero angle means no exclusion shaped the links there: interpolation then passes through 0° instead of spanning the band, and the outermost row cannot carry an angle into latitudes where none was seen. The rest are rounded down to 0.1°. When no band exceeds 0.05°, no min_exclude is declared. The set carries one all-orbits array (orb 0).

The pfd mask is not measured on the probe. The loop uses the profile’s declared mask, or computes one from every beam position the payload may take, visited or not, so a computed mask is conservative by construction. Where Declarations Come From explains why the probe is saturated, and why the declaration must not be measured on the run that later checks it.

A derived set describes one run

The derived values are what the system did, not what its rules allow. They are usually tighter than the profile’s rules, because an operation rarely sits on its limits. For example, a 10° elevation rule may give no link below 10.3°, and 10.3° is what the set declares.

A value well above the rule the profile enforces is a tendency of one finite run, not yet a promise. Before you file it:

  • raise the profile’s own rule to match, so that the scheduler (the part of the simulation that assigns satellites to locations) enforces what the set declares. The tech box From tendency to promise in Inside the Compliance Loop gives the steps;
  • check the result: run the system in the Simulation runner with the set in Operating params (optional).

The Compliance loop’s advisors work on the profile, not on the set. Apply to profile and Apply Nco rows (the per-latitude co-frequency caps) write rules the scheduler enforces; nothing they find is filed directly. So a cap an advisor writes and a derived max_co_freq row at the same latitude are different numbers: the first is a rule the operation obeys, the second is what the operation did under it.

Saving and exporting

  • Save set (JSON)… writes the set as *.opparams.json. This window, the Simulation runner and the Compliance loop read it.
  • Load set… opens a *.opparams.json, or a compliance-loop run’s *.operparams.json, and replaces every field.
  • Export R XML… writes the R-set XML for the SNS v10 builder. It refuses a set that breaks an encoding rule, and the red line says which.
Tech · the export rules

The set is written as the non_gso_operating_parameters element of S.1503-4 Part B. Export refuses a set that files a quantity in both forms, and enforces the encoding rules: min_duration is never written as 0 (leave it empty for the classic algorithm); min_angle_at_es is refused when min_duration is declared; es_density and es_distance are declared together, for a typical earth-station deployment, or both omitted, for specific earth stations; min_elev azimuths lie within 0 to 360°; a min_exclude orb is 0 or more. A declared min_duration asks the examination for the track-duration algorithm of S.1503-4 §D5.1.4.2. The Compliance loop does not build that algorithm: it examines such a set with the classic algorithm and says so.

Where the set goes

  • SNS v10 builder. In Masks and operating-parameter sets (f_mask R), add the XML with Add mask XML… and set the row’s f_mask to R. With at least one R row, the builder flags the notice for examination with its operating-parameter sets. The builder’s Design operating parameters… button opens this window.
  • Simulation runner. Put the JSON in Operating params (optional). The scheduler then obeys the set’s constraints instead of the profile’s own rules, in both directions; the payload and power still come from the profile. Run the same system with and without the set: the two equivalent power flux-density (epfd) distributions show what the declaration costs or allows.
  • Compliance loop. Put the JSON in Declared R set (optional). Run sweep examines a declared-mask profile against it; Run loop uses it instead of deriving a set.

The Simulation runner and the Compliance loop refuse a set filed in both forms.
