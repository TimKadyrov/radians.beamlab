Where Declarations Come From

Two places in this tool hand you an operating-parameter set: the compliance loop, and the R-set designer’s Derive & fill. They are not two measurements. There is one derivation, the loop owns it, and the designer reads what it produced.

The mechanism

Why the derivation comes first

A declaration is an envelope of what the system may do. Measure it while the system happens to be carrying light traffic and you measure what it did — then you have declared something the system will break the moment it gets busy. So the probe is saturated: demand rises to the declared co-frequency cap, and activity, illumination duty and operating fraction all go to 1. What is left shaping the result is only what the operator has actually committed to — the exclusion angle, the elevation floor, the caps, the minimum angles — plus what the geometry physically allows.

Worth a number

On the STEAM-2 case the profile asks for one link per cell but declares a cap of four. Derived from the traffic sample, MAX_CO_FREQ comes out as 1 — a promise the system breaks at peak. Derived from the saturated probe it comes out as 4, which is what the system is permitted to do and therefore what it must declare.

Why it cannot come from the truth sweep

The obvious shortcut — derive from the run that measures T — destroys the one test that matters. The examination must sit at or above the truth at every latitude: E1 ≥ T is what proves the declaration actually envelopes the system. A declaration measured on a particular run envelopes that run trivially, so deriving from the truth sweep would turn the test into a tautology. The probe is a different run by construction, which is what keeps the test honest.

The two runs also disagree on purpose. The probe is saturated and has no victim; the truth sweep carries the profile’s real traffic and a victim at every latitude. They are answering different questions, so they cannot be the same pass.

When adequacy fails

If E1 drops below T anywhere, the run says so and names the latitudes. That is a granularity failure of the derivation — the probe did not see enough of the system — and never a compliance failure of the system. The two must not be confused: one is fixed by measuring better, the other by redesigning.

What Derive & fill does now

It reads the loop’s run for the selected operation profile and fills every field from it. It does not simulate. The set you review is the set the projection actually used — not a second opinion about the same system that is free to disagree with it.

A run counts only when it is newer than the profile it claims to describe; an older run describes a system that has since been edited, so the designer treats it as absent and says so. When there is no run, the answer is to run the compliance loop — which derives the declaration as its first step.

The duration, time step and latitude-band inputs that used to sit on this panel are gone, and their absence is the point. Depth decides how conservative a declaration is: a shallower probe sees less of the system, so it produces a tighter and less conservative set, and no text box would have told the reader that. Depth belongs to the run that verifies the result, not to the panel that displays it.

What the designer still owns

  • Manual entry — copying an existing filing, or writing a deliberately conservative envelope by hand.
  • Review and hand-tightening — every field stays editable. A derived set is a proposal, not a verdict.
  • Export — the R-set XML the SNS builder consumes, and the JSON that round-trips.
