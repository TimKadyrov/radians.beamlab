radians.beamlab · the loop and the designer

Where Declarations Come From

Two of the declarations a filing carries describe how the system transmits: the pfd (power flux-density) mask and the R set of operating parameters. In this app both come from Run loop in the Compliance loop window, unless you supply them. The R-set designer’s Derive & fill measures nothing: it reads the R set the last loop run wrote. This page explains how the declarations are made, and why a declaration must not be measured on the run that later checks it.

How Run loop makes them

Run loop works in this order:

  • The R set is measured first, on a derivation probe: a separate simulation of the system with no victim and no limit, run at full load. What the probe observes becomes the declared operating parameters. Name a set in Declared R set to skip the probe and use that set instead.
  • The truth, T, is measured next: the equivalent power flux-density (epfd) the system produces as it operates, at a victim earth station at each latitude.
  • The pfd mask is not measured. It is the mask the profile names; a named file that is missing stops the run. Without one the run computes it from the payload’s reachable envelope: the strongest level any permitted beam position could produce, whether the probe visited it or not, and over every body yaw within the profile’s Yaw steering range when it gives one, so the mask is conservative by construction. Latitude rows from which no cell within the declared service latitudes can be reached are written as no transmission. The status line says which mask the run used.
  • The examination reads the R set and the mask the way Rec. ITU-R S.1503-4 does, at the same victims, and gives E1. The run then checks that E1 ≥ T at every latitude.

The run writes the profile, the R set and the mask, when it computed one, into one run directory, so they describe one system. The status line names the directory.

Tech · the computed mask

The mask is computed on the latitude step of the victim grid and a 1° azimuth/elevation grid. For each latitude row it takes the ascending and the descending ground-track headings, and it samples the band of sub-satellite latitudes the row governs at its centre and both edges, since S.1503-4 §D5.1.5 step 1 reads a row at the nearest latitude. A row is written as no transmission, the null value of S.1503-4 §C1, only under the service-span certificate: the band the row governs lies farther from the declared service latitudes (es_lat_min to es_lat_max) than the edge of a satellite’s coverage at the first shell’s operating height and the smallest declared minimum elevation, or 0° when none is declared. The certificate is closed-form and uses declarations only, never what the probe happened not to visit. A later run reuses the computed mask while it is newer than the profile and was made with the same latitude step, the same service latitudes and the same build of the app.

Tech · a mask you supply

A mask the profile names is examined as it is. It cannot be re-derived: a mask keeps only the strongest level in each direction and has lost which beam produced it. When the profile’s footprint source is that mask, Run loop checks whether it already carries the shaping the R set declares; Inside the Compliance Loop describes the check and its grades.

Why the probe runs at full load

A declaration is a bound on what the system may do. Measured while traffic is light, it records only what the system did, and the system breaks it the first time it gets busy.

So the probe is saturated: demand is raised to the declared co-frequency cap when one is declared, and activity, duty and operational fraction are set to 1. That takes the traffic out. What still shapes the result is the rules the scheduler enforces (the exclusion angle, the elevation floor, the caps, the minimum angles), the way it selects satellites, and the geometry.

A derived value tighter than the rule behind it describes one finite run, not a promise. Before filing it, tighten the enforced rule in the profile to match; Inside the Compliance Loop gives the steps.

Tech · the saturated probe

The probe is the operation profile with DemandLinksPerCell raised to the largest declared co-frequency cap (the largest max_co_freq row or header), and ActivityFactor, OperationalFraction and IlluminationDutyCycle set to 1. With no cap declared, the profile’s own demand stands. On the STEAM-2 test system the profile asks for one link per cell and declares a cap of four. Measured on the traffic as it runs, max_co_freq would come out as 1, a promise the system breaks at peak. The saturated probe measures 4 at every latitude band, which is what the system is permitted to do and therefore what it must declare.

Why not measure it on the truth sweep

Deriving the declaration from the run that measures T looks like a shortcut. It would turn the one test that matters into a formality.

E1 ≥ T asks whether the declaration covers the system. A declaration measured on a run covers that run automatically, so one taken from the truth sweep would always pass and prove nothing. The probe is a separate run, so the check can fail, and that is what makes it a test.

The two runs also answer different questions. The probe is saturated and has no victim. The truth sweep carries the profile’s own traffic and a victim at every latitude.

E1 below T at any latitude means the declaration does not cover the system, and Run loop names those latitudes. For a derived set, the derivation was too coarse: measure more finely, and never redesign the system to fix it. That is a different result from T itself failing the limit, which is fixed in the system.

What Derive & fill does

Pick the Operation profile and press Derive & fill. The designer finds the R set the loop last wrote for that profile and fills every field from it, except the identity (sat_name, ntc_id, param_id) and the band (low_freq_mhz, high_freq_mhz): those belong to your filing and stay as you entered them. It does not simulate. The set you review is the set the run examined, not a second opinion about the same system.

A run counts only when both hold:

  • it is newer than the profile file, since an older run describes a system that has since been edited;
  • it was made from this profile. Runs are filed under the profile’s name, so a run of the same name made from a different profile is refused: give the profile its own name, or run the loop for it.

When no run counts, the status line says so. Press Run loop in the Compliance loop window; it derives the declaration as its first step.

How deep the probe looks

Derive & fill has no duration, step or latitude-band inputs. The probe runs over the Compliance loop window’s Duration (days) / step (s), in latitude bands as wide as the step of ES lat from / to / step. Depth decides how much of the system the probe sees, so it belongs to the run that also checks the result.

On the 1 600-satellite STEAM-2 test system, the R set derived at 0.1 and at 1.0 day on a 60 s step was identical row for row, and the mask agreed to 0.01 dB in every lit cell. That is a measurement on one system, not a guarantee for every system.

What the designer is for

  • Manual entry: copying an existing filing, or writing a deliberately conservative set by hand.
  • Review: every field stays editable, and a derived set is a proposal, not a verdict. To check an edited set, save it with Save set (JSON)… and name it in Declared R set: Run loop then examines that set in place of deriving one, and still checks E1 ≥ T.
  • Export: Export R XML… writes the R-set XML to register in the SNS v10 builder; Save set (JSON)… writes the designer’s own format, which Load set… reads back.
